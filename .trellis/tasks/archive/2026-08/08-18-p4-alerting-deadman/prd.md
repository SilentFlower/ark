# P4-4 告警与死人开关

## Goal

让 Ark 在控制台之外主动暴露两类失联风险：

1. `ark-hub` 按现有健康投影发现备份超时、连续失败或恢复演练失败时，向钉钉群发送具备静默期的告警。
2. `ark backup` 每次实际运行结束后向外部监控发送心跳，由 Ark 进程之外的系统发现调度、主机或 Ark 整体停止工作。

## Background

- P4-2 已在 `internal/hub/health.go` 建立唯一健康投影，稳定告警种类为
  `backup_overdue`、`backup_consecutive_failures`、`verification_failed`。
- `/api/alerts` 当前每次请求实时计算告警，`created_at` 是投影时刻，不是首次发生时间；现有状态库不保存告警历史或投递状态。
- `ark-hub` 不承载备份调度；备份仍由 systemd timer 启动 `ark backup`。停止 Hub 不得影响备份和恢复演练。
- 超时告警不能只依赖备份结束事件触发，因为“备份没有运行”本身就是必须发现的故障，因此钉钉投递需要由 Hub 周期评估当前健康投影。
- 死人开关不能由 Hub 发送；Hub 自己停止时仍必须由 `ark backup` 的外部心跳暴露调度存活状态。
- 清单严格拒绝未知字段，现有敏感值均通过受限文件间接引用；钉钉 webhook/token、签名密钥与心跳 URL 中的秘密不得进入 API、日志、错误、状态库或示例明文。

## Requirements

### R1 告警来源与一致性

- 钉钉告警必须复用现有 Hub 健康投影，不在通知层重新实现超时、连续失败或演练失败判定。
- schedule 无法解析、健康为 `unknown` 时不得伪造超时告警。
- 告警稳定标识使用现有 `<host>:<kind>`，同一活动故障在多次评估间保持一致。

### R2 钉钉投递

- Hub 在后台按固定周期评估当前告警；首次发现活动告警时发送 Markdown 消息。
- 消息至少包含 host、稳定 kind 的中文说明、检测时间和当前相关运行状态，不包含清单路径、SSH、repo、Cookie、token、原始 stderr 或状态库原始 JSON。
- 钉钉凭证从权限受限的独立文件读取，清单只保存绝对路径；文件缺失、类型错误、权限过宽、格式错误或发送端点不安全时 fail closed。
- HTTP 客户端必须有明确超时、响应体上限和受限重试；发送失败不得阻塞 Hub HTTP 服务，也不得把凭证写入日志或状态库。

### R3 静默状态

- 静默期必须跨 Hub 重启生效，因此投递状态通过 `store.Store` 的公开 API 持久化，Hub 不持有 `*sql.DB` 或自行拼 SQL。
- 状态至少能区分告警首次发现、最近一次成功投递、当前是否仍活动以及恢复时间。
- 同一告警的并发评估不能产生重复发送；数据库时间统一使用 UTC Unix 毫秒。
- 首次发现活动告警时立即发送；故障持续期间每 24 小时最多重发一次。
- 告警恢复时发送一次恢复通知；恢复后再次出现视为新一轮告警并立即发送。
- 只有成功投递才开始或刷新 24 小时静默期；发送失败按受限退避重试，不能因失败进入整日静默。

### R4 外部心跳

- 心跳只由非 `--dry-run` 的 `ark backup` 发送；`--dry-run` 不产生任何网络请求。
- 心跳发生在本次备份已形成最终摘要之后，覆盖全量、`--host`、systemd 和 Hub 手工触发的同一 CLI 路径。
- 采用供应商无关的成功/失败双端点：`ok`、`warn` 调用成功端点，`fail` 调用失败端点。
- 两个端点通过独立权限文件提供；允许两者配置为同一 URL，以兼容只关心任务存活、不区分结果的监控服务。
- Ark 不实现 Healthchecks.io 专用 `/start`、run ID 或运行时长协议；使用该服务时由管理员把基础 URL 和 `/fail` URL 分别配置为两个端点。
- 心跳请求必须有明确超时、响应体上限和脱敏错误；URL 或认证材料不得进入 stdout、stderr、状态库或 manifest。
- 心跳投递结果进入人类摘要和 `--json` 的 `heartbeat_status`，稳定取值为
  `disabled`、`sent`、`failed`，但不写入 run 状态或 manifest。
- 心跳投递失败不得改变 `ark backup` 的既有退出码和 run 状态；已完成的备份事实不能因监控网络故障被改写为失败。
- 清单已成功加载后发生的 backup 前置失败、取消或最终 `fail` 使用失败端点；清单本身无法加载时无法安全取得秘密文件路径，只能由外部监控在宽限期后发现缺失心跳。

### R5 兼容性与运维

- 未配置钉钉或心跳时保持现有行为，不新增网络请求，不影响现有 P0-P4-3 部署。
- `ark validate`、`ark doctor`、示例清单、README、设计文档和路线图与新增配置同步。
- `ark-hub.service` 仍独立于所有 backup/verify timer；停止 Hub 后备份与心跳仍可执行。

## Acceptance Criteria

- [ ] 同一投影输入下，API 与钉钉发送使用完全一致的三类告警集合。
- [ ] 首次活动告警立即发送，持续故障每 24 小时最多重发一次；静默期内不重复刷群，Hub 重启后状态不丢失。
- [ ] 恢复时只发送一次恢复通知，恢复后复发立即发送；状态转换有数据库与 Hub race 测试。
- [ ] 钉钉超时、非 2xx、超大响应、非法 JSON/业务错误和重试均有测试，任何错误都不泄露凭证。
- [ ] `ark backup` 的 ok/warn 终态调用成功端点，fail 终态调用失败端点；前置失败与取消路径有明确、受测语义。
- [ ] `--dry-run` 与未配置场景零网络请求；心跳失败不会伪造备份快照或篡改已持久化 run 事实。
- [ ] 心跳网络失败时 `heartbeat_status=failed`，原本 ok/warn 的 backup 退出码仍为 0；原本 fail 的退出码仍为 1。
- [ ] 配置未知字段、相对路径、权限过宽、符号链接和秘密回显均被拒绝或覆盖测试。
- [ ] `make check`、相关 race 测试、常规与 `CGO_ENABLED=0` 构建、`git diff --check` 全部通过。
- [ ] 真机人为制造连续两次备份失败后，控制台与钉钉在一个评估周期内同时出现告警；静默期内不重复发送。
- [ ] `systemctl stop ark-hub` 后 backup timer 与外部心跳继续工作；停止 backup timer 后外部监控能按其宽限期报告失联。

## Out of Scope

- 在 `ark-hub` 内接管 backup/verify 调度。
- 新增告警确认、手工静默或告警历史管理页面。
- 短信、电话、邮件、DING 等钉钉 webhook 之外的通知渠道。
- 自动故障切换、DNS 切换或 P5 dnsmgr 联动。
- 由 Ark 自己判断外部监控是否已经报警；死人开关的超时判定归外部监控所有。
