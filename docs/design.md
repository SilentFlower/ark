# ark 设计文档

> 本文记录 ark 的设计目标、架构决策和取舍理由。
> 实现细节以代码为准，但**为什么这么做**只记录在这里。

## 1. 背景

生产服务用 docker compose 部署在若干台机器上。当前的风险是：

- 机器可能突然宕机、被回收、磁盘损坏，短时间内拿不回任何数据。
- 已有的主备流复制方案（如果有）解决的是「机器挂了切过去」，**解决不了误删表、
  升级写坏数据、勒索软件加密**——这类逻辑错误会实时同步到备机。
- 应用自带的数据库备份只覆盖数据库。机器整个没了之后，手上有一个 `.sql.gz`，
  但没有 compose 文件、没有 `.env`、没有数据卷、不知道当时跑的是哪个镜像，
  **新机器依然拉不起来**。

**复制不是备份。** ark 要解决的是后者：一份能回到过去某个时间点、
且独立于生产机器存在的完整副本。

## 2. 目标与非目标

### 目标

- **整机可重建**：在一台干净的新服务器上，用一条命令把服务完整拉起来，
  包括数据库、数据卷、编排文件、配置密钥和镜像身份。
- **跨机器**：多台机器共用一套工具和一个对象存储，任意一台的备份可以在任意一台上恢复。
- **可观测**：一个 Web 页面能看到所有机器的备份状态，谁多久没备份了一眼看见。
- **可验证**：备份能被自动演练恢复，而不是等到真出事那天才知道它是坏的。
- **长期可维护**：单个静态二进制，无运行时依赖，配置声明式且拒绝静默失败。

### 非目标

- **不做秒级 RPO**。默认 24 小时，可配到小时级。要做到「恢复到误删前一秒」需要
  WAL 归档（pgBackRest / wal-g），复杂度高一个量级且只覆盖 PostgreSQL，
  暂不纳入。见 §11。
- **不做自动故障切换**。ark 只负责备份和恢复，不参与流量调度、不做 fencing、
  不自动提升任何节点。
- **不做通用备份平台**。范围严格限定在 docker compose 部署形态。

## 3. 组件与信任边界

```
┌──────────────┐   备份数据(加密)   ┌────────────────────┐
│  机器 A      │ ─────────────────► │                    │
│  ark agent   │   状态元数据       │   对象存储 (R2/S3) │
│  (oneshot)   │ ─────────────────► │                    │
└──────────────┘                    │  <host>/           │  restic repo
┌──────────────┐                    │    ...             │
│  机器 B      │ ─────────────────► │  _status/          │  状态 JSON
│  ark agent   │                    │    web-01.json     │
└──────────────┘                    │    db-01.json      │
                                    └────────────────────┘
                                              │ 只读 _status/
                                              ▼
                                    ┌────────────────────┐
                                    │  中心机 ark-hub    │
                                    │  Go + 内嵌前端     │
                                    │  总览 / 告警       │
                                    └────────────────────┘
```

三个组件的职责边界：

| 组件 | 职责 | 拥有的权限 |
|---|---|---|
| `ark`（每台机器） | 执行备份和恢复 | 自己 prefix 的读写 + 自己的 restic 密码 |
| 对象存储 | 存放加密备份和状态元数据 | — |
| `ark-hub`（中心机） | 展示状态、告警 | **只读 `_status/` prefix，没有 restic 密码** |

关键性质：**中心机拿不到任何备份内容。** 它只能看到「web-01 在 04:17 备份成功，
1.2GB，5 个目标全部完成」这样的元数据。中心机被拿下不会导致备份泄露，
中心机宕机也不影响备份继续执行。

## 4. 关键决策

### ADR-001：用 restic，不自己写备份引擎

自己实现增量、去重、加密、完整性校验和保留策略，等于把 restic 重写一遍且没经过考验。
ark 真正的价值在**编排层**：知道该备份什么、按什么顺序恢复。

restic 直接提供：内容寻址去重、客户端加密（对象存储被拖库也读不了）、
快照语义、多后端（S3/R2/SFTP/本地）、`restic check` 完整性校验、`forget --prune` 保留策略。

代价：多一个外部二进制依赖。可接受——`doctor` 会检查它存在。

### ADR-002：push 模式，不做中心机拉取

每台机器主动推送到自己的 prefix，各自持有只能写自己 prefix 的凭证。

被否决的方案是「中心机 SSH 到各机器执行备份并拉回」：那台中心机会同时成为
单点故障和横向移动入口——拿下它等于拿到所有生产机的 SSH 权限。
备份系统的中心节点是攻击者的高价值目标，不应该让它持有生产机凭证。

中心机因此退化为**只读观测面**，见 ADR-006。

### ADR-003：数据库走逻辑备份，绝不打包 PGDATA 卷

运行中的 PostgreSQL 数据目录做热拷贝，得到的是撕裂的、不一致的快照，
恢复时可能根本起不来，而且**在恢复之前你不会知道**。

因此 postgres 类型固定走 `docker compose exec -T <service> pg_dump`。
Redis 同理，先 `BGSAVE` 再取 RDB。

只有确定与数据库无关的卷（上传文件、静态资源）才允许直接打包。

### ADR-004：镜像用 digest 不用 tag

备份时记录容器实际运行镜像的 `RepoDigests`（`repo@sha256:...`），恢复时按 digest 拉取。

tag 是可变的。半年后的 `myapp:latest` 可能已经是三个大版本之后，
数据库 schema 与备份内容不兼容，恢复出来的服务会以难以诊断的方式失败。

### ADR-005：oneshot 进程 + systemd timer，不做常驻 daemon

agent 由 systemd timer 触发，跑完退出。

常驻进程会引入一整类故障：进程自己崩了、内存泄漏、时钟漂移导致漏跑，
而且**没有任何外部信号**——你以为它在跑，其实三个月前就死了。
systemd timer 由 init 系统保证调度，agent 只需要保证自己跑一次是对的。

配套决定：调度表达式用 systemd `OnCalendar` 语法而非 cron 语法，
语法校验直接委托给 `systemd-analyze calendar`，避免自己写一个近似的解析器。

### ADR-006：中心机只读状态元数据，不直连 restic 仓库

`ark-hub` 不持有任何 restic 仓库密码，也不调用 restic。
它展示的所有信息来自 agent 每次运行后写到 `_status/<host>.json` 的状态文件，
其中包含快照列表摘要（由 agent 侧执行 `restic snapshots --json` 后提炼）。

这样中心机的权限降到最低：一个只读 `_status/` 的对象存储凭证。
代价是页面上的数据有延迟（取决于备份频率），可接受——
观测面本来就不需要实时。

### ADR-007：清单里的未知字段一律报错

YAML 解析开启 `KnownFields(true)`。写错一个字段名会立刻失败，而不是被静默忽略。

对普通应用，静默忽略未知配置只是小问题；对备份工具，它意味着
**你以为某个目标在备份、实际它从未被执行过**，而这个事实只会在
真正需要恢复的那天暴露。

同理，`Validate` 也会拒绝「字段填在了错误的类型下」，例如给 `redis` 目标写 `database:`。

### ADR-008：静态校验与环境校验分离

- `ark validate` 只检查清单本身，全程不碰文件系统和 docker。
  因此中心机可以校验任意一台机器的清单副本。
- `ark doctor` 检查这台机器上是否真的能执行——命令是否存在、
  密钥文件权限是否安全、compose 里是否真有这个 service、volume 是否真的存在。

备份系统最常见的失败模式不是代码写错，而是**三个月前某个前提条件悄悄变了而没人发现**。
`doctor` 把这些前提条件变成可以定期自动检查的断言。

## 5. 备份清单

每台机器一份 `/etc/ark/ark.yaml`，完整示例见 [`examples/ark.yaml`](../examples/ark.yaml)。

五种备份目标：

| 类型 | 做什么 | 必填字段 |
|---|---|---|
| `postgres` | `pg_dump` 逻辑备份 | `service`, `database` |
| `redis` | `BGSAVE` 后取 RDB | `service` |
| `volume` | 打包整个 docker volume | `name` |
| `files` | 备份宿主机路径 | `name`, `paths` |
| `image_digest` | 记录运行镜像 digest | `services` |

## 6. 备份流程

```
ark backup
  ├─ 加载并校验清单
  ├─ doctor 前置检查（失败即中止，不产生半成品快照）
  ├─ 逐个执行 target，输出流式送入 restic
  │    postgres → pg_dump      → restic backup --stdin
  │    redis    → BGSAVE + cp  → restic backup --stdin
  │    volume   → tar          → restic backup --stdin
  │    files    → restic backup <paths>
  │    image_digest → docker inspect → JSON → restic backup --stdin
  ├─ 写入快照清单（记录本次包含哪些 target、各自的 restic snapshot ID）
  ├─ restic forget --prune 按保留策略清理
  └─ 写 _status/<host>.json（供中心机展示）
```

任一 target 失败都会让整次备份标记为失败并在状态文件中记录，
但**已成功的 target 不会回滚**——半份备份也比没有强。

## 7. 恢复流程

恢复的顺序不能错，否则会得到一个看似启动成功、实际数据不完整的服务：

```
ark restore --host web-01 --snapshot latest [--dry-run]
  1. 拉取快照清单，展示将要恢复的内容和目标位置
  2. 恢复 files（compose 文件、.env、反代配置）
  3. 按记录的 digest 拉取镜像
  4. 创建 volume 并恢复卷数据
  5. 只启动数据库服务，等待健康
  6. psql 灌入 pg_dump 数据；Redis 放置 RDB 后启动
  7. 启动应用服务
  8. 输出健康检查结果和需要人工确认的项（DNS、证书、端口）
```

强制要求：

- **`--dry-run` 必须只读**，不创建容器、不写文件、不改动任何状态。
- **幂等**：中途失败后重跑同一条命令必须能继续，而不是留下半个环境。
- **不允许隐式覆盖**：目标机器上已存在同名 volume 或容器时必须显式确认。

## 8. 密钥与信任边界

这是整个系统**最容易致命**的部分。

需要在生产机之外独立保管的密钥：

| 密钥 | 丢失后果 |
|---|---|
| restic 仓库密码 | **所有备份变成无法解密的废数据** |
| 对象存储凭证 | 无法访问备份（可在控制台重新签发，不致命） |
| 应用 `.env` 中的加密密钥 | 数据库能恢复，但加密字段全部读不出来 |

规则：

1. `repo.password_file` 的内容必须同时存在于密码管理器或离线介质中。
   只存在于生产机上的仓库密码，在机器损毁时和没有备份是等价的。
2. 所有密钥文件权限必须是 `0600`，`ark doctor` 会强制检查。
3. 清单文件本身不含密钥（只含文件路径），但含仓库地址，
   因此 `.gitignore` 排除真实清单，只提交 `examples/`。

## 9. 状态上报与中心机

agent 每次运行后写 `_status/<host>.json`，内容包括：

- 主机与项目标识、agent 版本
- 本次运行的开始/结束时间、结果、耗时
- 每个 target 的结果、大小、restic snapshot ID
- 最近若干个快照的摘要
- 下一次计划运行时间（来自 `systemd-analyze calendar`）
- 最近一次 `doctor` 报告

`ark-hub` 聚合所有 `_status/*.json` 并提供 Web 页面：

- **总览**：每台机器一张卡片——最近备份时间、状态、大小趋势、下次计划时间
- **告警**：超过约定时长没有成功备份的机器标红；对接钉钉机器人推送
- **详情**：单机的 target 明细、历史快照、doctor 报告

前端技术栈与现有项目保持一致：Vue 3 + Vite + TypeScript + Pinia + Tailwind，
构建产物用 `go:embed` 打进 `ark-hub` 单二进制，部署时不需要 node 环境。

## 10. 恢复演练

**没有验证过的备份等于没有备份。**

`ark verify` 定期（建议每周）挑一个快照，恢复到一个隔离的 compose 项目
（不同 project-name、不同端口、独立 volume），跑健康检查，通过后销毁。
结果写入状态文件，在中心机页面上作为一等公民展示。

不做这件事，最可能的结局是：`pg_dump` 三个月前就在报错，
而你在需要恢复的那天才发现。

## 11. 已知风险与未决问题

| 风险 | 现状 | 缓解 |
|---|---|---|
| RPO 最坏等于一个备份周期 | 默认 24h | 可配到小时级；需要更小则要上 WAL 归档 |
| `pg_dump` 版本必须 ≥ 服务端 | 未处理 | doctor 应增加版本比对（待实现） |
| 大库全量逻辑备份耗时长 | 未处理 | restic 去重只减少传输量，不减少 dump 时间 |
| 恢复到新机器后 IP/域名变化 | 未处理 | 恢复后输出人工确认清单（DNS、证书、防火墙） |
| 对象存储账号本身被封 | 未处理 | 后续支持同时写入第二个后端 |
| 单机多 compose 项目 | 未支持 | 清单当前假设一台机器一个项目 |
